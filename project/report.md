## 1. Паспорт проекта

- **Название проекта:** Прогнозирование ежедневных продаж розничной сети по категориям товаров.
- **Автор:** Шевцов Андрей Олегович
- **Группа:** ИНБО-22-24
- **Контакт:** tg: @gnomik101
- **Ссылка на шаблонный репозиторий:** `https://github.com/mirea-aie-2025/aie-student-template`

- **Краткое описание:**  
  Проект решает задачу прогнозирования количества продаж (`Units Sold`) для каждой категории товаров розничной сети на 7 дней вперёд.

  Используются синтетические данные о продажах, классические модели временных рядов (наивный, скользящее среднее, Ridge-регрессия) и нейронная сеть GRU.

  Результат – REST API на FastAPI, которое по идентификатору категории и историческим значениям возвращает недельный прогноз.

## 2. Постановка задачи и контекст

**Предметная область и задача:**  
Розничная торговля. Менеджерам необходимо понимать будущий спрос в разрезе товарных групп (Groceries, Furniture, Electronics, Clothing, Toys) для управления запасами, планирования закупок и акций. Задача – многомерный прогноз временных рядов.

**Пользователь сервиса:**  
Сотрудник отдела закупок или категорийный менеджер. Сценарий: пользователь передаёт историю дневных продаж конкретной категории и получает прогноз на следующую неделю для оценки потребности в товаре.

**Формулировка ML-задачи:**  
- Вход: последовательность длины ≥ 28 дней – суммарные дневные продажи категории.  
- Выход: 7 чисел – прогноз продаж на последующие 7 дней.  
- Ограничения: точность прогноза должна позволять оперативное планирование (MAE не превышает 30–50% среднедневных продаж). Интерпретируемость не критична, но важна стабильность работы сервиса.

**Целевые метрики качества:**  
MAE (средняя абсолютная ошибка) и RMSE (корень из среднеквадратичной ошибки). MAE легко интерпретировать в натуральных единицах (штуках), RMSE сильнее штрафует большие отклонения. Обе метрики считаются на валидационной и тестовой выборках.

  - В датасете представлены как числовые, текстовые и категориальные данные.
  - Для задачи прогнозирования используются `Date`, `Category` и **целевая переменная `Units Sold`**.

EDA и визуализация рядов по категориям выполнены в ноутбуке `notebooks/01_eda_baseline.ipynb`.

## 4. Модели и подходы

1. **Базовые (baseline) модели:**
  Все baseline модели, которые будут описаны в данном разделе, представлены в `./notebooks/01_eda_baseline.ipynb`

  - **B1 – Naive (последнее значение):** прогноз равен последнему известному дню. Служит нижней границей качества. Значения метрик: 
    - Средний mae по всем категориям = 701
    - Средний rmse по всем категориям = 877
  - **B2 – Moving Average (окно 7):** среднее арифметическое последних 7 дней. Простая модель, устойчива к шуму. Значения метрик:
    - Средний mae по всем категориям = 632
    - Средний rmse по всем категориям = 785
  - **B3 – Ridge-регрессия:** линейная модель с L2-регуляризацией, обученная на 11 признаках (лаги, rolling, календарные). Показывает, насколько полезны созданные фичи. Значения метрик:
    - Средний mae по всем категориям = **581**
    - Средний rmse по всем категориям = **730**

2. **Улучшенные модели и эксперименты:**  
   
   В файле `./src/train.py` проводились эксперименты по улучшению модели GRU путём подбора размера окна и числа слоёв. Текущие значения, описанные в следующем пункте, дали лучший баланс качества и времени обучения для данной модели.

3. **Нейросетевые модели (если применимо):**

    В качестве нейросетевой модели выбрана **рекуррентная сеть GRU** с окном 28 дней. Гиперпараметры: скрытый размер 64, 2 слоя, batch 64, learning rate 0.001, оптимизатор Adam, функция потерь MSE, 30 эпох.  
   Для каждой категории обучалась отдельная модель GRU (свой scaler).
   Значения метрик:
     - Средний mae по всем категориям = 617
     - Средний rmse по всем категориям = 777

## 5. Экспериментальный протокол и результаты

Здесь важно показать, что выбор финальной модели был осмысленным.

1. **Экспериментальный протокол:**
  Данные каждой категории разбивались хронологически: 70% train, 15% validation, 15% test. Метрики MAE и RMSE для всех моделей рассчитывались на валидационной выборке. Для GRU дополнительно проводилась оценка на тестовой выборке, подтвердившая отсутствие переобучения (значения на тесте не уступали валидационным).

2. **Сравнение моделей по метрикам:**

  | Категория   | B1 Naive (MAE/RMSE) | B2 MovAvg (MAE/RMSE) | B3 Ridge (MAE/RMSE) | R1 GRU (MAE/RMSE) |
  |-------------|----------------------|-----------------------|----------------------|--------------------|
  | Groceries   | 963.56 / 1113.08     | 717.22 / 833.50       | 682.26 / 795.60      | **538.51 / 691.12** |
  | Furniture   | 683.49 / 889.62      | 746.64 / 961.88       | **569.49 / 729.67**  | 657.35 / 827.92    |
  | Electronics | 684.76 / 858.18      | 557.07 / 687.76       | **512.67 / 654.04**  | 660.70 / 826.51    |
  | Clothing    | 573.17 / 734.66      | 550.93 / 702.56       | **540.94 / 713.97**  | 601.55 / 745.45    |
  | Toys        | 604.40 / 793.44      | **592.06 / 739.38**   | 600.06 / 756.14      | 626.50 / 793.19    |

3. **Выбор финальной модели:**  
   В качестве финальной модели для сервиса выбрана **Ridge-регрессия**.  
   Она показала наилучшие средние показатели MAE (~581.1) и RMSE (~729.9) по всем пяти категориям, а также лидирует на трёх из них (Furniture, Electronics, Clothing).  
   По сравнению с GRU, Ridge значительно проще: не требует подбора архитектуры, быстрее обучается и не нуждается в масштабировании целевой переменной.  
   Trade-off: на категории Groceries GRU даёт выигрыш в точности (MAE 538.5 против 682.3 у Ridge), однако ради унификации сервиса и стабильности прогнозов на остальных категориях предпочтение отдано Ridge. При необходимости в будущем можно реализовать динамический выбор модели для каждой категории.

## 6. Архитектура решения и сервис

1. **Архитектура пайплайна:**
  1. `src/data.py` – загрузка сырых данных, агрегация продаж по `Category` и `Date`.  
  2. `src/features.py` – расчёт лаговых, rolling и календарных признаков.  
  3. `src/models.py` – реализация baseline-функций, Ridge и класса GRUForecaster.  
  4. `src/train.py` – обучение моделей для каждой категории, сохранение моделей, scaler’ов, сводной таблицы метрик.  
  5. `src/service.py` – FastAPI-приложение, загружающее модели и scaler’ы при старте, предоставляющее `/predict`.

2. **API и endpoints:**
  - `GET /health` – возвращает `{"status":"ok"}`.  
  - `POST /predict` – принимает JSON: `{"category":"Groceries","history":[val1,val2,...]}`. Возвращает: `{"forecast":[pred1,...,pred7]}`. Ограничения: длина `history` ≥ `window_size` (28), категория должна быть одной из обученных. Интерактивная документация доступна по `/docs` (Swagger UI).

3. **Технологический стек:**

Python 3.10+, FastAPI, PyTorch, scikit-learn, pandas, NumPy, uvicorn.  
Docker не используется, развёртывание – локально по инструкциям `README.md`.

## 8. Ограничения и дальнейшая работа

**Текущие ограничения:**
- Прогноз строится только на истории продаж (лаги, скользящие статистики, календарные признаки), без учёта внешних факторов (промо-акции, погода, праздники, цены). Это ограничивает точность в периоды аномального спроса.
- Для всех категорий используется единая модель Ridge, хотя для Groceries GRU показала лучшие метрики (MAE 538.5 против 682.3). Унификация снижает потенциальную точность на этой категории.
- Итеративный прогноз на 7 дней с пересчётом признаков на каждом шаге может накапливать ошибку, особенно при резких изменениях тренда.
- Модель обучена на фиксированном наборе данных (2022–2023) и не обновляется автоматически — со временем возможен дрейф прогнозов.
- Отсутствует оценка неопределённости: прогноз точечный, без доверительных интервалов.

**Что можно улучшить при наличии времени:**
- *Модель:* динамический выбор модели (Ridge или GRU) для каждой категории по валидационным метрикам; добавление экзогенных признаков (Weather Condition, Holiday/Promotion, Price) для повышения точности.
- *Сервис:* вероятностное прогнозирование (квантильная регрессия, бутстрап); асинхронная обработка и кэширование.
- *Данные и эксперименты:* регулярное переобучение с мониторингом дрейфа; ансамблирование; исследование кросс-категорийных взаимодействий.
